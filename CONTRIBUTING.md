# Contributing to squalify

squalify is an Apache-2.0 .NET 10 library (`squalor.squalify`) and .NET tool (`squalify`, package `squalor.squalify.Cli`). It profiles one data file and writes a deterministic JSON descriptor. It does not reference DataBall; the schema in [`docs/descriptor.md`](docs/descriptor.md) is the contract. If you use squalify rather than change it, start with the [user guide](docs/user-guide.md).

Coding agents: [`AGENTS.md`](AGENTS.md) adds the agent-specific rules on top of this page.

## Prerequisites

The .NET SDK pinned by [`global.json`](global.json) (10.0.x). Nothing else is needed to build and test.

## Layout

- `src/squalify/`: the library: pipeline stages (sniff, format detection, format profilers, field profilers), the descriptor model and the writer.
- `src/squalify.Cli/`: the `squalify` tool.
- `tests/squalify.Tests/`: xUnit tests for the library. Fixtures are under `tests/squalify.Tests/fixtures/`, with golden descriptors (`<fixture>.squalify.json`) next to them.
- `tests/squalify.Cli.Tests/`: xUnit tests for the CLI (run in-process through `CommandFactory.InvokeAsync`), the NuGet packages and the Markdown docs.
- `schema/`: `descriptor-v1.schema.json`, the JSON Schema (2020-12 subset) of the descriptor. The tests in `tests/squalify.Tests/Schema/` validate every golden against it with an in-repo validator, and keep its members, enums and rules equal to `docs/descriptor.md` and to the code.
- `docs/`: the guides, `descriptor.md` (schema), `design.md` (architecture), `how-it-works.md` (diagrams), `release.md`. `docs/reviews/` holds generic write-ups of real-sample findings; `docs/process/` holds process notes.
- `scripts/`: `corpus-check.sh`.
- `.github/workflows/`: `ci.yml` (build, test, format on Windows, macOS and Linux) and `release.yml`.

## Build, test, format

```bash
dotnet build squalify.sln -c Release
dotnet test squalify.sln -c Release
dotnet format squalify.sln --verify-no-changes
dotnet run --project src/squalify.Cli -c Release -- profile <file>   # run the CLI from source
```

Run the first three before you send a change; CI runs them on all three operating systems.

## Tests

- **Categories.** `Category=Package` tests pack both NuGet packages and check them: each nupkg holds the README (the repository's bytes), the XML doc file and the license expression, plus the icon, the symbols, the tool command, and a consumer that restores the library from a local feed and writes the CLI's bytes (they run `dotnet`, so CI runs them as their own step). `Category=Corpus` tests profile a private directory and are excluded from CI. `Category=Large` tests stream gigabytes to bound process memory; they take a long time and are run by hand. Everything else is plain xUnit. CI's test step is `--filter "Category!=Corpus&Category!=Package&Category!=Large"`; locally, `--filter "Category!=Corpus&Category!=Large"` runs everything CI runs.
- **Package validation.** `dotnet pack` of the library runs package validation against a baseline release from nuget.org (`PackageValidationBaselineVersion` in `src/squalify/squalify.csproj`), so a 1.x change that removes or renames a public member or changes a signature fails the pack. `dotnet restore` fetches the baseline into the NuGet cache (the first restore needs the network; the Package tests and `--no-restore` packs read it from the cache), and the CLI tool project is not validated. A Package test removes a public member from a copy of the library and expects the pack to fail. Only constructors and `Deconstruct` of the positional model records and the provisional model types of the user guide may be suppressed in 1.x, each with a user-guide "Breaking changes" entry in the same commit; any other error is a bug. After each release is listed on nuget.org, the next commit to `main` moves the baseline up to it and drops the suppressions that are no longer needed. Only a stable release moves the baseline (a prerelease value fails the Package test). The test `Suppressions_AreAllowedKindsWithAUserGuideEntry` checks that every entry of `src/squalify/CompatibilitySuppressions.xml` is one of those kinds and that its type is named in a user-guide entry for a version newer than the baseline. See [Package validation](docs/release.md#package-validation).
- **Throughput benchmark.** `tests/squalify.Tests/Bench/ThroughputTests.cs` measures squalify on generated streams (no file on disk): a plain 12-column table and a wide padded one (256 columns of 64-byte right-padded cells, a key preamble, annotation rows and a header, so about 89 percent of its bytes are padding; 256 fields is at most 547, so the sketches run at full precision, level 0 of [Bounded memory and sketches](docs/design.md#bounded-memory-and-sketches); the wide shape therefore does not exercise sq-38's precision scaling, which the 2,000-column test in the suite does). For each shape it times reading the source alone, the byte pass alone and the full profile, and records wall time, MB/s (10^6 bytes), cells per second (data rows x columns) and the peak working set, each in a fresh child process. Run it by hand, alone, with `dotnet test tests/squalify.Tests/squalify.Tests.csproj -c Release --filter "FullyQualifiedName~ThroughputTests&Category=Large" --logger "console;verbosity=detailed"`: `Bench_PaddedWide_1Gb` and `Bench_Plain_1Gb` assert that the growth of the peak working set over a small-stream baseline stays within `MemoryBudget.CeilingBytes`; `Bench_PaddedWide_4Gb` only records. Timings are never asserted. The memory assertions assume the default workstation concurrent GC: under server or non-concurrent GC the growth can exceed the ceiling by GC slack (seen at 16 MiB), so the ceiling is asserted only by the Large tests. The same code runs at 16 MiB in ordinary tests, which check that every pass counted every byte and that the peak could be read (and that the ceiling assertion itself fails for a low ceiling), and by hand at any size with `dotnet tests/squalify.Tests/bin/Release/net10.0/squalify.Tests.dll --throughput-probe Full PaddedWide 268435456` (passes `Drain`, `BytePass`, `Full`; shapes `Plain`, `PaddedWide`). Each result prints a readable line, a raw `key=value` line to paste into a note, and a context line (OS, architecture, runtime, CPU count, GC mode, library version, commit); the commit is not in the assembly, so set `SQUALIFY_BENCH_COMMIT=$(git rev-parse --short HEAD)` for the run to record it. The figures inform any decision to fuse the passes; the benchmark changes no design.
- **Golden descriptors.** Every supported format has golden tests: the descriptor for a fixture is compared byte for byte with `<fixture>.squalify.json`. After an intended output change, rewrite them with `SQUALIFY_UPDATE_GOLDEN=1 dotnet test squalify.sln -c Release`, then review the diff before you commit it.
- **Determinism tests** profile the same fixture twice, and under a different culture, and compare the bytes.
- **Fixtures.** No GB-scale fixtures in the repository; large-file behavior is tested with generated streams. Real samples never enter the repository: write findings up generically under `docs/reviews/`.
- **Private corpus.** `scripts/corpus-check.sh [--require-golden] <dir>` profiles a directory outside the repository (determinism, repeat runs, goldens next to the files). It runs by hand. A file with no `<file>.squalify.json` next to it is reported as `no golden`, not as passed: it was profiled and found deterministic, but compared with nothing, so a green run covers a format only where goldens exist. The script's last lines count the entries apart, for example `corpus: 1 passed, 0 failed, 1 no golden; 1 entry has no golden and is not passed (--require-golden makes that a failure)`, and the exit status is still 0 unless an entry failed. With `--require-golden` (the script sets `SQUALIFY_REQUIRE_GOLDEN=1`, which the harness reads; setting the variable yourself does the same) an entry with no golden fails the run: the exit status is non-zero and the summary says `FAILED: require-golden is set (--require-golden or SQUALIFY_REQUIRE_GOLDEN=1)`. The `Category=Corpus` tests are two theories: `Corpus_EachFile_Passes` for entries with a golden, and `Corpus_EachFile_HasNoGolden_NotCompared` for entries with none (it passes unless a golden is required; the script's per-file list labels those entries `No golden`). `SQUALIFY_UPDATE_GOLDEN=1` writes or rewrites the golden of every entry inside `<dir>`, existing goldens included, so use it only to record or accept the current output. The harness writes only under `<dir>`: `.squalify-corpus/run.log` and `.squalify-corpus/summary.txt`. The harness's own tests (`CorpusTests`, `CorpusNoGoldenTests`) use a synthetic directory and run in CI; only the `Category=Corpus` theories, which read the real directory, are excluded.
- **Docs tests.** Relative links in `docs/*.md`, `CONTRIBUTING.md` and `AGENTS.md` must resolve, fixtures named in the guides must exist, and the README, which ships in both packages and renders on nuget.org, must use only absolute URLs.
- **Mutation-check new tests:** break the product code, confirm the test goes red for the right reason, then revert.

## Code rules

- Every source file starts with `// SPDX-License-Identifier: Apache-2.0`. The namespace is `squalor.squalify` (with `.Cli` for the tool). Source is ASCII.
- Nullable is on. Public members carry XML doc comments.
- Public failures surface as `SqualifyException`. Wrap lower-level exceptions instead of leaking IO types.
- **Determinism is a hard rule.** Output must not depend on the current time, culture, machine, path, thread scheduling, hash-seed randomization or dictionary enumeration order. Format numbers with the invariant culture and shortest round-trip formatting, and sort every collection by a documented key. Output-affecting math uses only IEEE `+ - * /` and `Math.Sqrt`; logarithms go through `DetMath` and sketch hashing through `XxHash64`; never use `Math.Log`, `Exp` or `Pow`, or `string.GetHashCode`, in output paths. The one runtime dependency is the descriptor writer's escaping of unassigned code points, so descriptor bytes are guaranteed only within one .NET runtime major version; fingerprints are runtime-independent. The full rules are in [`docs/design.md`](docs/design.md#determinism-rules).
- No ML, no LLM calls, no network access.
- Literal data values appear in a descriptor only under `--include-values` or `--include-values-for` (see `ValuesPolicy` and [the values tier](docs/design.md#values-tier)).
- Prefer the BCL and in-repo code. Ask the owner before adding any package. Approved dependencies: System.CommandLine 2.0.11 (CLI), and in the test projects only Microsoft.NET.Test.Sdk 17.14.1, xunit 2.9.3 and xunit.runner.visualstudio 3.1.5.
- A descriptor schema change updates `docs/descriptor.md` and bumps `schemaVersion` according to the policy there, in the same commit: the first schema-changing commit after a release bumps it and points `$id` at `v<schemaVersion>.0`, the final tag of the coming release (the schema tests tie it to the const), and later ones before the next release share the bump. The `$id` is the same for every patch and prerelease of the series, so an rc and its final share one `$id`, and a release only checks it.
- **Making a planned member, family or dialect produced.** This is a schema change, so the rule above applies, and so does this list: the STDF profiler, the `kind` rules and the other members that [`docs/descriptor.md`](docs/descriptor.md#planned-for-a-1x-minor-release) marks planned each go through every area below in one commit. The list is what the change that made the Touchstone and key=value families produced (sq-09) had to touch; drop an item that does not apply, and add one when a change finds an area the list misses. A test (`Contributing_FlipChecklist_NamesOnlyWhatExists`) ignores the comments of the C# files and fails when a type, a member named as Type.Member (a declaration-shaped member in a file that declares the type), a test method, a path, a schema definition named as $defs.X (a key of `$defs` in the schema) or a quoted section or phrase on a doc line below no longer exists, or when an area is missing; it does not check that the prose is right.
  - Code. Register the profiler in `FormatRegistry.Default` (`FormatRegistry.Order` is fixed). A new result member goes in `FormatProfile`, which `Profiler` copies into `Descriptor` and into `ProjectionInput`. Add the family's contributor to `FingerprintContributors.All`. A new issue code goes in `IssueCodes` and `IssueCodes.All`. A new region kind also goes in `InvalidByteLocator.RegionKinds`. A new member of a model record joins the record's Equals and GetHashCode; prefer an `init` member, because it needs no constructor suppression, whereas a positional member needs a compatibility suppression (see Package validation above) and a user-guide "Breaking changes" entry (see "Non-positional records" in [`docs/design.md`](docs/design.md#determinism-rules)). Write it in `DescriptorWriter` in the documented key order, and set `Descriptor.SchemaVersion`.
  - Schema. In `schema/descriptor-v1.schema.json`: the `schemaVersion` const and `$id`, the family enum, the dialect `oneOf` and the dialect `$defs`, the new members, and the enums they extend (`$defs.issueCode`, `$defs.regionKind`, `$defs.issueRegion`). A member that the new family does not write moves from required to optional.
  - Tests. `SchemaValueTests` (the enum pins and the `schemaVersion` row), `PlannedMembersTests` (its planned families and labels), `DocumentedMembersTests` (the planned list in `Schema_PlannedMembers_AreTheOnesNothingProducesYet`) and `DocumentedMembers` (a new dialect needs its `(family)` row marker mapped to `#<family>Dialect`) and `DescriptorInvariants` (the rules per family). The candidate lists of `ProfilerTests` and `FormatRegistryTests`, which hold every registered profiler. The hard-coded schema version in `SchemaTests` and `KeyValueTests`, and every test whose fixture now classifies as the new family. Fixtures for the new family, with a canary in `tests/squalify.Tests/fixtures/canary` named in `ValuesTierTests.CanaryFixtures`, and a check in `FormatRegistryTests` that no existing fixture is reclaimed. The key-order pin `PlannedMembersTests.KeyOrderPin` (`tests/squalify.Tests/fixtures/full-binary-stdf.squalify.json`) holds members that nothing produces yet and goes when a real golden pins them. Every golden re-recorded and its diff reviewed. A docs test for the change of family, as `Docs_SayWhichFilesChangeFamilyIn110` in `tests/squalify.Cli.Tests/DocsTests.cs` does.
  - `docs/descriptor.md`: the "Top level" table, the key-order rows ("Key order of nested objects") and "Optional versus null"; the "format.dialect by family" table and its sentence on what is produced; the family's section on its layout and table (as "layout of a Touchstone file"); "Planned for a 1.x minor release" and "Interim members"; the "issues[]" and "evidence[]" tables and the "Values tier" list; the "Versioning policy" and an entry under "Changelog".
  - `docs/design.md`: the "v1 formats" row, the score table under "Choosing a format", a section for the family (as "Touchstone"), the limits table under "Bounded memory and sketches" and "Structural fingerprint".
  - `docs/user-guide.md`: the "Formats" table and the paragraph on files that change family, the table under "Values policy", the "Versions" and "Model records" bullets and the "API added in" and "Breaking changes in" entries of "Guarantees and stability", and "Troubleshooting".
  - `README.md`: the "Status" line.
  - `docs/how-it-works.md`: the "Status" banner (the series is set at release), the diagrams and their `Source:` lines under "The pieces", "Choosing a format", "What is always included, and what needs --include-values" and "Fingerprints and hints", and a section for the family's own algorithm (as "Touchstone files and key=value documents"). A diagram marks a profiler that is not built "(planned)".
  - Corpus check. Real samples never enter the repository. From a checkout of `main`, record goldens with `SQUALIFY_UPDATE_GOLDEN=1 scripts/corpus-check.sh <dir>` over a private directory. Then run `scripts/corpus-check.sh <dir>` from the branch's worktree, and list every failed entry whose `format.family` changed. Put those cases in the changelog and the user-guide paragraph; a generic write-up goes under `docs/reviews/`. The goldens stay beside the private files.
- **Closed sets have one place in the code.** Issue codes are in `IssueCodes` (`src/squalify/Descriptor/IssueCodes.cs`), evidence stages in `EvidenceStages` and the interim kind labels and rule ids in `InterimKinds`. To add an issue code, add its field and its place in `IssueCodes.All`, then the schema enum (`$defs.issueCode`) and the tables in `docs/descriptor.md`; to add an evidence stage, do the same in `EvidenceStages` and its `Order`. Every `new Issue(` and every call of `LocatedIssue` takes its code from an `IssueCodes` field: a test reads the compiled code and fails for any `Issue` construction that has no load of an `IssueCodes` field since the previous construction in the same method, so a literal, a variable, a concatenation of those and a field of another class are caught (only the record's compiler-made copy constructor and the `Profiler.LocatedIssue` forwarder are exempt, by name). It does not prove that the loaded field is the code: an expression that also loads a registry field (`IssueCodes.RaggedRows + suffix`, `IssueCodes.All[i]`) passes, and review and the goldens against the schema cover that. The registry holds `static readonly` fields, not constants, so that a use of it is a field load in the compiled code and a literal is not. The tests in `tests/squalify.Tests/Schema/` fail until the registry, the schema and the document agree. `SqualifyErrorCodes` (the values of `SqualifyException.Code`) is the exception to the `static readonly` rule: its values are `const`, because consumers use them in `case` labels, so moving them to `static readonly` later would be a source break.
- README and `docs/` change in the same commit as the behavior they describe.

## Docs

- The README is a front page and is packed into both NuGet packages: keep it short, and link to the guides with absolute `https://github.com/squalor-xyz/squalify/blob/main/...` URLs. Other docs use relative links.
- Guides ([getting started](docs/getting-started.md), [user guide](docs/user-guide.md), [examples](docs/examples.md)): every command and output excerpt must come from a real run on a committed fixture. Move content instead of duplicating it.
- `docs/how-it-works.md` explains the pipeline with Mermaid diagrams. It is the only copy (no committed renders); GitHub renders the Mermaid blocks.
- Diagram rules: plain-language labels with the type or method name in `<small>` text; one idea per diagram; each diagram names its source file, or "(planned)" until the code exists.

## Tracking and slices

Roadmap, slices and goals are tracked with the `slicer` CLI (`slicer ai` explains the workflow): `slicer next` shows the next ready slice and `slicer show <id>` prints its spec. Change that state only through `slicer`, never by editing `.slicer/`. Work for a slice happens on a branch `<id>` in a git worktree under `.worktrees/<id>` (git-ignored). Write the slice's named tests first and watch them fail for the stated reason.

## Releases

A release is a `vX.Y.Z` tag equal to `<Version>` in `Directory.Build.props`; the release workflow publishes both packages to nuget.org. Steps and the workflow's checks are in [`docs/release.md`](docs/release.md).
